Commands

Unpack the tarball into an empty directory, then:

cd weft-sandbox-v0.1

# Phase 0 — Litmus suite (24 cells: 8 tests × 3 languages × 2 build modes)
make litmus        # → litmus/REPORT.md + litmus/results.json

# Phase 1 + 5 — Benchmark suite (B-cells + W-cells)
make bench         # → bench/results.json (canonical) + bench/results/wsuite-*.json

# Phase 5 — Static site regeneration (this site)
make site          # → bench/site/index.html etc.

# Phase 4 — Port structural validation
make validate      # → 4/4 targets exit 0

# Phase 5 — Full clean-tree validation (runs all five)
make all

sha256 expectation honesty

The canonical B-suite bundle bench/results.json is pinned in the whitepaper at sha256 16b5c663.... Re-running make bench will produce a DIFFERENT sha256 — benchmark numbers contain timing data, and re-running any benchmark lawfully produces a different hash. This is documented in WO-P5-RELEASE decision 1:

The tarball ships the Phase 1 bench bundle (bench/results.json, sha256 16b5c663) as-is — it is the whitepaper's pinned single source. The make bench release gate verifies the harness runs green, NOT that it bit-reproduces 16b5c663: results.json contains timing data, and re-running any benchmark lawfully produces a different hash. A re-run that overwrote the shipped bundle would silently break the whitepaper's hash index and Appendix A contract.

The make bench release gate therefore:

  1. Runs the harness against a scratch output path
  2. Verifies all cells pass (exit 0)
  3. Discards the scratch output
  4. Verifies the shipped canonical bundle's sha256 still matches 16b5c663...

If your re-run produces a different sha256 for the canonical bundle, that is expected and OK — the shipped bundle is the pinned single source, not a reproducible artifact. The whitepaper's hash index references the shipped bundle's sha256, not your re-run's.
